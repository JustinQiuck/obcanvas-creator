# 项目记录格式

当前格式版本为 1。正式记录放在资料库 `影视项目/` 下，以稳定 ID 关联；文件名、路径和标题不作为记录身份。

```yaml
---
obcanvas:
  version: 1
  kind: shot
  id: 唯一镜头编号
  sceneId: 所属场次编号
  title: 镜头标题
---
镜头正文，可以包含普通 Markdown。
```

场次使用相同命名空间，`kind` 为 `scene`，无需 `sceneId`。界面创建时生成 UUID。P0-A 的编号只用于显示；D06 起使用场次 `shotOrder` 保存正式成片顺序。

- `obcanvas` 是插件管理的属性组，标题通过镜头卡编辑，正文可以通过镜头卡或原生笔记编辑器编辑。原生属性面板可能把嵌套属性组显示为对象；无需在该面板编辑它。
- 其他属性、YAML 注释及插件不拥有的字段被保留；只改标题时正文逐字保留。YAML 库可能调整属性的空格排版。
- 更新在 `Vault.process()` 中对照初始版本、最新文件及本地输入。不同字段可合并，同字段发生分歧时拒绝覆盖。
- 文件重命名后按 ID 重新定位；删除、重复 ID、损坏属性或未知版本不自动重建、不覆盖。
- `data.json` 保存未提交的编辑草稿及其冲突基线；0.4.0 增加非敏感的 `ai.baseUrl` 与 `ai.model` 配置，同一入口合并写入，保留已有草稿与其他字段。它不是第二份正式镜头记录，密钥由宿主 SecretStorage 保存。保存成功或明确放弃本地修改后清除相应编辑草稿。未知格式草稿阻止插件初始化并保留文件。
- 本版本支持候选与采用，尚无关键帧格式或旧画布批量迁移；各阶段扩展见下文。

## D04：画布布局与视口

`影视项目/画布布局.json` 是版本 1 的布局记录。`scenes[场次ID].positions[镜头ID]` 保存 `{x,y}`；`scenes[场次ID].viewport` 保存 `{x,y,k}`，作为新视图默认视口。文件不包含镜头标题、正文、素材内容或采用决定。

已经打开的标签页各自持有视口，随 Obsidian 工作区保存，不会因为另一个标签页缩放而跳动。卡片位置在不同标签页之间共享。初次显示卡片时登记默认位置，以后按镜头 ID 恢复，不按文件扫描次序移动已有卡片。位置不代表正式成片顺序。

布局变更合并进 `Vault.process()` 读取的最新文件，拖动过程中延迟 180ms 合并写入，关闭视图时也会尝试写入。写入失败显示错误并保留内存里的待保存位置，可点击“重试保存布局”；请在重试成功后退出应用。未知版本或无效坐标拒绝写入并保留原文件。

## D05：库内素材关联

镜头的 `obcanvas.media` 是可选列表，旧记录无此字段仍可正常打开：

```yaml
  media:
    - id: 素材稳定编号
      path: 素材/参考图.png
    - id: 另一素材编号
      path: 素材/短视频.mp4
```

通过中文选择器从当前资料库选取文件；同一文件重复关联同一镜头不增加副本，关联到另一个镜头时复用已有素材 ID。关联不代表采用。移除关联只改镜头记录，不删除图片或视频。

路径必须是库内相对路径，不能是绝对路径、网络 URL 或包含 `..` 的路径。播放 URI 由 `Vault.getResourcePath()` 在运行时解析，不写入笔记。尺寸与时长来自图片／视频元素读取到的元数据，无法读取时显示未知或明确的解析错误；本版本不持久化这些技术属性。

插件运行时监听文件及文件夹重命名，更新使用该路径的镜头；素材 ID 不变。文件缺失保留原关联，显示缺失提示。“重新关联”会更新所有引用同一素材 ID 的镜头；如果目标文件已有素材 ID，使用目标身份；目标在同一镜头中已存在时拒绝合并，需明确移除旧关联。不保证跨多个镜头文件的一次性事务，某文件写入失败会报告错误，允许重新关联继续修复。

插件关闭期间的文件移动无法自动推断身份；重新打开后会提示缺失，可手动重新关联。图片选择支持 PNG/JPEG/WebP/GIF/AVIF，视频选择支持 MP4/WebM/MOV/M4V/OGV；扩展名可选不保证其中所有编码都能播放，实际解码由 Obsidian 的 Chromium 决定。首轮只验证了 PNG 与 H.264 MP4。

## D06：镜头规划、正式顺序与选片

插件 0.2.0 继续读取版本 1 记录，以下均为可选扩展；P0 笔记无需重建。含选片数据的资料库应使用 0.2.0 或后续版本编辑，旧插件不具备采用保护。

场次的 `obcanvas.shotOrder` 保存镜头 ID 数组。创建镜头后追加到场次顺序，上移／下移只改场次笔记，卡片坐标不变。旧笔记中没有登记顺序的镜头按稳定 ID 放在末尾；首次新增或调整顺序后写入正式数组。删除镜头后残留 ID 不显示，恢复相同 ID 的笔记按现存顺序数组重新定位。

创建镜头和追加场次顺序是两次文件写入。若第二步失败，镜头文件保留，界面明确提示“镜头已创建，但顺序保存失败”，可从列表调整顺序恢复，不需要重复创建。

镜头可选文字字段：`intent`（拍摄理由）、`framing`（景别）、`camera`（机位与运动）、`prompt`（原提示词）、`source`（来源备注）。这些字段与标题、正文一样受草稿备份和逐字段并发检查保护；未知信息可留空或写 TBD。提示词与来源备注是镜头层面的文字，不会调用生成服务。

视频的关联项可增加：

```yaml
  media:
    - id: 视频一的稳定编号
      path: 素材/版本一.mp4
      decision: candidate
    - id: 视频二的稳定编号
      path: 素材/版本二.mp4
      decision: rejected
      reason: 动作不连贯，需要重做
```

- 没有 `decision` 的旧视频按候选处理。`candidate`／`adopted`／`rejected` 分别对应候选／采用／退回；退回必须有非空原因。
- 同一镜头最多采用一份视频；选择另一版本时，旧采用版本恢复为候选，文件继续保留。取消采用、恢复候选是明确操作，会清除当前退回原因；本批不保存决定的完整历史日志。
- 决定属于当前镜头的关联项。同一个素材 ID 在另一个镜头中可以有不同决定与原因。
- 每次选片在 `Vault.process()` 内核对提交前的视频 ID、路径、决定和原因。过期表单拒绝覆盖；同一镜头的选择切换只写一个笔记，不涉及跨文件采用事务。
- 已采用视频不能直接移除关联或替换源文件；需先取消采用。文件改名保留决定。更换未采用素材时清除旧决定，让新文件重新候选；目标素材在同一镜头已存在时拒绝合并，避免吞掉决定。

状态优先级：有采用视频 → 已采用；有未退回的视频 → 待选片；所有视频均退回 → 待重做；没有视频但有正文、理由或景别 → 待素材；其余 → 待规划。图片不算生成视频。文件缺失／无法读取独立提示，不抹掉已采用或已退回的事实；已采用也不等于已剪辑完成。

“复制文件到资料库”或向当前镜头素材区域拖入系统文件，会复制至 `影视项目/素材/唯一编号-原文件名`，不移动／覆盖原始文件。小于等于 256 MB 的单文件支持直接复制；更大的文件先放入资料库，再用库内选择器关联。复制成功但关联失败时保留副本，并显示其位置供重新关联。库外路径直连与自动导入历史项目仍未支持。

## 0.3.0：自由卡片和用途关系

版本 1 格式增加 `script`（剧本）、`person`（人物）、`setting`（场景资产）、`frame`（已有关键帧）、`asset`（通用素材）类型。它们与镜头一样具有 `sceneId`、标题和正文，沿用同一编辑冲突检查和草稿备份；`scene` 仍表示场次，不表示场景图片。旧镜头笔记无需迁移。

卡片可使用既有 `media` 列表引用库内文件。视频采用和退回只由目标镜头的 `media` 项保存，素材节点不存第二份决定。同一素材在多个镜头中可以分别采用或退回。文件改名处理扩展到所有卡片类型。

用途连线保存在目标卡片的 `obcanvas.links`：

```yaml
  links:
    - id: 连线UUID
      from: r:来源卡片UUID
      role: 人物参考
```

`from` 的 `r:` 表示卡片记录，`m:` 表示媒体 ID；可用用途为参考、剧情拆分、人物参考、场景参考和起始帧。UI 中的「视频候选」直接使用目标镜头的 `media` 关联投影，不同时写入 links。来自旧镜头的媒体在画布中投影为素材卡，无需复制或迁移正文。链接来源缺失时保留关系并提示，不静默删除。

布局的记录卡位置继续以记录 ID 为键，旧镜头坐标原样读取；无独立记录的媒体位置以 `m:媒体ID` 为键。布局仍不包含正文、连线语义或采用决定。卡片标题变化不改变任何关系。

当前起始帧关系只表示用户选取的已有图像，不包含视频来源时间、采用区间或续接验证。创建关联不会自动证明图像与镜头内容相符。

## 0.4.0：拍摄资产与提取清单

继续读取格式版本 1，新增 `prop`（道具）。人物、场景与道具在项目范围复用，`sceneId` 保留创建场次含义，不再限制使用范围；不批量重写旧卡片。

剧本的 `links` 可增加 `role: 拍摄资产`，`from` 必须指向有效的人物／场景／道具记录（`r:资产ID`）。使用已有 ID，不复制资产笔记。当前画布显示本场次卡片以及它们引用的其他场次资产，布局仍按场次分别记录。新增“道具参考”可供手动关联镜头。

资产可选字段：

```yaml
  assetDetails:
    unresolved: [服装待确认]
    needs: [主参考, 妆造]
  media:
    - id: 图片稳定编号
      path: 影视项目/素材/参考图.png
      purpose: 主参考
      confirmed: true
      fingerprint: 影视项目/素材/参考图.png:修改时间:字节数
```

`unresolved` 保存影响当前制作的疑问，`needs` 至少一项参考用途。旧资产无该字段时以“主参考”为默认需求，不自动写回。图片导入时没有确认状态，用户选择用途并确认后才写入 `confirmed` 与文件指纹；这与镜头视频的 `decision` 分开。文件缺失或指纹变化要求复核。文件改名时，只有原文件状态仍匹配才保留确认；替换文件需重新确认。

提取结果保存为 `影视项目/资产整理/任务UUID.json`，与正式 Markdown 资产分开。任务记录包括格式版本、递增 revision、剧本／创建场次 ID、输入摘要、原剧本文字、模型和 Skill 版本、时间、状态，以及清单条目。条目含名称、类型、原文依据、描述、待确认信息、参考需求、create／reuse／ignore 决定、目标 ID 和已处理标记。

输入摘要为剧本 ID、场次 ID、标题、正文的 SHA-256，应用前及逐项写入前核对；只改变关联不让剧本输入过期。草稿保存对照完整初始内容，拒绝覆盖外部修改。正式创建前保存预分配 ID，创建笔记的 `source` 记录任务与条目来源；中断后按同一 ID 恢复，不能用重试覆盖其他身份的记录。

`review` 为待确认，`applying`／`partial` 均可恢复未完成保存，`complete` 表示这次清单已应用。完成任务记录仅保留当时的建议与映射；之后资产正式内容及图片确认以资产笔记为准。重新提取不会自动删除旧清单或旧资产。

含 `prop`、拍摄资产关系或参考确认字段的资料库应继续使用 0.4.0 或后续版本。旧插件不了解新增语义，不能把安装文件备份当作自动降级数据迁移。

### 0.4.1：逐项校验问题

提取清单增加可选 `issues: string[]`（最多 100 项，每项最多 1000 字），记录模型返回顺序、资产名称及未通过的字段原因。旧清单无需迁移。`items` 只保留通过检查的条目，确认只处理这些条目；全部失败时保留问题清单，但不能确认空清单。问题在清单重开或插件重启后继续保留，不保存完整失败响应。

解析允许空描述／待确认信息省略或为 null，并接受单个文字参考用途。原文依据只兼容空白和换行差异，保存前还原为剧本中的连续精确片段；不接受改写、省略或非连续拼接。复用目标仍必须存在且类型相符。

### 0.4.2：删除与恢复

删除卡片通过 `Vault.trash(file, false)` 将对应笔记移至库内 `.trash`，不更改格式。其他记录中指向该 ID 的关系、场次 `shotOrder` 与布局坐标保留；缺失卡片不参与画布渲染或当前镜头排序。用户将笔记放回原位置后可恢复原 ID、关系和布局。资产提取清单保留为历史，不随删除自动重新创建资产。场次不在卡片删除范围内。

纯 `m:` 素材节点不对应独立笔记，移除时仅清除当前场次记录中的该素材关联及指向其 `m:` 身份的连线。源文件与其他场次不变；已采用视频阻止移除。多记录移除按笔记保存，失败可重试，不保证跨文件事务。

### 0.5.0：Skill 配置与运行快照

`影视项目/技能配置.json` 保存 `version: 1`、`defaultAssetSkillId`、`scripts`（剧本 ID 到显式 Skill ID 的覆盖映射）和 `custom`。未覆盖的剧本跟随项目默认；没有配置文件的旧资料库使用内置通用剧情资产规则，只读取不会创建文件。配置独立于插件 `data.json`，模型设置和编辑草稿保存不会覆盖它。

自定义项包含 `id`（custom- 前缀）、`name`、`stage: assets`、`version`（每次保存生成新版本标识）和 `instructions`（最多 20000 字）。最多 100 项。Markdown 导入创建新的本地身份，不使用外部 ID 覆盖内置规则；只支持文字正文，不读取引用文件或执行脚本。`stage` 明确为其他阶段时拒绝导入资产入口。

配置写入在 `Vault.process` 中比对最新配置与编辑基线；异常保留原文件与当前编辑。缺失选定 Skill 会阻止运行，不静默换用默认。已加载的配置文件被移除时要求恢复，不自动重建。

提取任务新增可选 `skill`，保存实际选中的 ID、名称、阶段、版本、原始规则及 `prompt`（注入统一输出协议后发送的完整 system 内容）。旧任务无此字段仍可读取，UI 标记为旧版记录。运行启动时复制快照，后续规则修改不影响在途请求、历史清单或正式资产。`skillVersion` 与快照版本一致。分镜预览任务见下节；图片与视频提示词阶段尚未实现。

## 0.6.0：分镜预览任务

0.7.0 继续兼容本任务格式，界面入口已移至项目的“分镜”工作区。新剧本的输入摘要同时包含 `projectId`，旧摘要算法保持兼容。

分镜预览保存到 `影视项目/分镜设计/任务UUID.json`，与正式 Markdown 镜头分开。格式版本为 1，包含任务 ID、递增 revision、剧本／场次 ID、输入摘要、原剧本文字、创建时间、模型、状态、问题列表，以及实际使用的分镜 Skill 和完整 system prompt 快照。

每个预览镜头包含稳定的任务内 ID、名称、连续逐字原文依据、拍摄理由、景别构图、机位与摄影机、起点、主要动作、终点、声音、静态起始关键帧提示词和 `plannedDurationSeconds`。该时长表示成片计划，不表示视频模型生成时长。任务状态固定为 `review`；0.6.0 没有“应用为正式镜头”动作。

输入摘要覆盖剧本身份、标题、正文和已通过 `拍摄资产` 关系连接的人物／场景／道具文字、待确认信息、参考需求及已确认图片用途。未关联资产和图片路径不进入模型上下文。剧本或关联资产变化后，旧预览保留供对照并标记过期。

模型返回逐项校验：原文必须能还原为剧本中的连续精确片段，全部拍摄字段非空，计划时长大于 0 且不超过 120 秒。无效镜头写入 `issues`，有效镜头继续保留；这只证明结构可用，不证明景别选择或关键帧质量已经通过人工审查。编辑使用完整基线做乐观冲突检查，取消和迟到响应不创建任务，重开从 JSON 恢复。

## 0.7.0：剧本项目归属

新增 `kind: project`，项目 ID 为稳定 UUID；`legacy-project` 保留给旧资料。新场次、剧本、镜头与资产增加 `obcanvas.projectId`。剧本和镜头仍要求 `sceneId`；人物、场景、道具、素材、关键帧在具备 `projectId` 时可没有场次。

归属优先级为记录 `projectId` → 所属场次 `projectId` → `legacy-project`。旧数据读取不落盘；首次为原有项目改名时，只增加项目笔记。缺失项目或场次和项目归属不一致会显示错误。编辑身份检查包含项目，新增引用只允许同项目；AI 上下文、候选复用和画布投影也在数据层过滤。

技能配置新增可选 `projects: {项目ID: 默认资产SkillID}`；优先级为剧本覆盖 → 项目默认 → 旧默认。项目名称不参与关联，改名不改变引用。项目库、列表和详情都是原记录的视图，不另存一份资产数据。Obsidian 视图状态新增 `library: {projectId, section, scriptId}`，原布局和草稿继续兼容。

## GS01a 开发候选：正式镜头与分镜方法

本节为尚未发布的源码行为；正式资料库仍使用 0.8.0。旧笔记和 `review` 任务向前兼容，读取时不迁移；新应用状态的任务不保证可由 0.8.0 读取，因此测试只在隔离资料库进行。

正式镜头沿用 Markdown 正文作为 `action` 的唯一内容来源，不增加第二个可编辑动作属性。`obcanvas` 新增可选文字属性 `start`、`end`、`sound`、`keyframePrompt`、`plannedDuration`，与原 `intent`、`framing`、`camera` 一起保存。`plannedDuration` 是秒数字符串，空值表示未设定，非空时大于 0 且不超过 120；它是计划剪辑时长，不是生成时长。`keyframePrompt` 是文字，不代表已有关键帧图片；旧 `prompt` 原样保留，尚未实现生成段执行文案。

确认预览采用新增方式：展示新增数与已有镜头保留说明，用户确认后创建镜头。不会推断新预览和既有镜头的替换关系。初次写入前，任务冻结 `application: [{ itemId, shotId, applied }]`；目标 ID 对齐全部预览条目且不重复。状态依次为 `review` → `applying` → `complete`，失败记 `partial`，意外退出保留 `applying` 也可继续。开始应用后预览冻结，正文编辑在正式镜头进行。

每镜写入后保存进度。重试按原 ID 检查来源及归属，保留人工修改，仅补齐未完成写入/场次排序；标记已应用的镜头若被删除则要求恢复，不从任务重建。每步重读源剧本与关联资产摘要；过期任务仅供回查。历史选择器可访问旧预览；重新生成不会隐式删除旧任务或镜头。GS01a 初始实现使用场次 `shotOrder`；GS01b 启用项目顺序后的行为见下节。

独立文件 `影视项目/分镜方法配置.json`：`version: 1`、`custom` 分镜规则数组、`projects` 项目默认方向表、`scripts` 剧本覆盖表。方向包含 `skillId`、`format: drama | mv`、`direction`、`musicTiming`。优先级为剧本 → 项目 → 内置剧情方法，与原资产 Skill 文件分开。自定义只保存文字规则，每次修订生成新版本；任务记录启动时的完整 Skill、实际 system prompt 和 `direction` 快照。MV 必须选择自定义分镜方法并填写音乐依据，存在这些字段不等于其质量经过验证。

方法编辑需明确保存；工作区切换前提示保存或放弃。尚未保存的方法表单不提供关闭整个插件后的草稿恢复，已保存的方法和预览均从资料库恢复。配置冲突、损坏及运行中观察到的文件丢失均保留原数据并报错，不静默切回默认。

## GS01b 开发候选：全片顺序

项目 `obcanvas.editOrder?: string[]` 保存同项目正式镜头的稳定 ID，全片只有此处可写顺序。属性缺失代表尚未启用，空数组代表已确认但尚无已排镜头。重复 ID、非项目记录上的该属性被格式校验拒绝；引用存在但属于其他项目或非镜头的记录会作为目录问题报告，不允许继续排序。

首次“整理全片顺序草案”按当前场次列表及旧 `shotOrder` 展示提案，读取和改动草案不写笔记。用户确认后才写项目字段；原有虚拟项目仅新增项目笔记，不改写所有旧镜头。未在旧场次顺序中的镜头按稳定 ID 展示供检查，这个显示次序不是已确认的跨场次剪辑次序。

启用后，全片列表只显示已排且仍存在的镜头；场次列表由全片次序筛选得到。缺少于 `editOrder` 的新镜头单独显示待排；手工创建和 AI 确认入卡均不擅自排到片尾，也不再写旧场次 `shotOrder`。在全片草案中“排到片尾”并确认才纳入顺序。未启用的项目保留原场次排序功能，已启用项目的旧排序按钮关闭，存储入口也拒绝旧方式改序。

删除不清除 `editOrder` 中的原 ID；缺失项不占当前可见序号，内部位置保留。移动可见镜头时交换对应位置，缺失项仍留在原位置，恢复同 ID 笔记后再次显示。未知新 ID 不可添加；已有缺失 ID 不可从草案删除。整个项目删除仍按子记录、场次、项目的顺序移入回收站，项目字段随同项目笔记保留。

顺序草案保存项目基线及结构摘要，结构包含顺序、镜头/场次身份与归属，首次初始化还包含旧场次顺序。保存时重查结构，在 `Vault.process` 内核对最新项目顺序；正文、标题、媒体与画布位置不进入顺序冲突摘要。保存失败保留当前窗口草案；正式镜头已创建但尚未排序时仍是待排，可重新准备顺序而不重建镜头。未保存顺序在关闭插件后不恢复，退出工作区时需确认保存或放弃。

旧版插件不理解项目顺序，不应与开发版同时写同一资料库；回退需要相应数据备份，不能仅替换插件文件。本轮仅验证隔离资料库，没有执行正式格式升级。
